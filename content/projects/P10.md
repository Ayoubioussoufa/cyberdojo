Most cloud breaches come from configuration, and they leave a detailed record. In this project you build the mistakes yourself, read that record, and fix the mistakes in code.

The attack here is safe by design: instead of breaking in, you'll simply use the over-powerful role yourself, on your own account, and see what its credentials could reach. That's the same trail that an attacker would leave. To practise real cloud attacks, use [flAWS](http://flaws.cloud/) or [CloudGoat](https://github.com/RhinoSecurityLabs/cloudgoat).

@term Terraform state = The file where Terraform records what it has created.
@term assume a role = Exchange your identity for a role's temporary credentials.

::: law Your own account, and watch the bill
Use a separate AWS account, used for nothing else. Set a budget alarm first, as in [lesson 63](/courses/0063-cloud-foundations-and-iam/). Put only fake data in it. Run `terraform destroy` when you finish each session.
:::

## Step 2: Install the AWS CLI

@help aws-cli guided

The **AWS CLI** controls AWS from your terminal, which is the same API that the website uses. On Kali:

```bash
curl "https://awscli.amazonaws.com/awscli-exe-linux-x86_64.zip" -o "awscliv2.zip"
unzip awscliv2.zip
sudo ./aws/install
aws --version
```

Create an access key for your lab user in the console, then connect:

```bash
aws configure
aws sts get-caller-identity
```

`aws configure` asks for the key, the secret and a region: use `eu-west-1`. It stores them in `~/.aws/credentials`. The second command asks "who am I?", and it should print your user. Delete this key when the project ends, because long-lived keys are exactly what you've learned to fear.

@done `aws sts get-caller-identity` shows my lab user.

## Step 3: Install Terraform

@help terraform guided

**Terraform** builds infrastructure from text files, so that it can be reviewed, repeated and destroyed. On Ubuntu or Kali:

```bash
wget -O - https://apt.releases.hashicorp.com/gpg | sudo gpg --dearmor -o /usr/share/keyrings/hashicorp-archive-keyring.gpg
echo "deb [arch=$(dpkg --print-architecture) signed-by=/usr/share/keyrings/hashicorp-archive-keyring.gpg] https://apt.releases.hashicorp.com $(grep -oP '(?<=UBUNTU_CODENAME=).*' /etc/os-release || lsb_release -cs) main" | sudo tee /etc/apt/sources.list.d/hashicorp.list
sudo apt update && sudo apt install terraform
terraform version
```

Kali's codename isn't one that HashiCorp's list knows. If that fails there, install Terraform on your Ubuntu machine, or use the zip file from [the install page](https://developer.hashicorp.com/terraform/install).

@done `terraform version` works.

## Step 4: Build the flawed environment

Create a new repository called `cloud-lab`, and add `terraform.tfstate*` and `.terraform/` to its `.gitignore`, because state files can hold secrets. Create `main.tf`:

```hcl
terraform {
  required_providers {
    aws = {
      source  = "hashicorp/aws"
      version = "~> 6.0"
    }
  }
}

provider "aws" {
  region = "eu-west-1"
}

# The data an attacker would want. Only fake data goes here.
resource "aws_s3_bucket" "reports" {
  bucket_prefix = "dojo-reports-"
  force_destroy = true
}

resource "aws_s3_object" "fake_customers" {
  bucket  = aws_s3_bucket.reports.id
  key     = "customers.csv"
  content = "name,email\nTest Person,test@example.com\n"
}

# Too much power: this role can do anything to any bucket.
# The second principal lets you assume it, to see what its credentials can reach.
data "aws_caller_identity" "me" {}

data "aws_iam_policy_document" "trust" {
  statement {
    actions = ["sts:AssumeRole"]
    principals {
      type        = "Service"
      identifiers = ["ec2.amazonaws.com"]
    }
    principals {
      type        = "AWS"
      identifiers = [data.aws_caller_identity.me.arn]
    }
  }
}

resource "aws_iam_role" "app" {
  name_prefix        = "dojo-app-"
  assume_role_policy = data.aws_iam_policy_document.trust.json
}

resource "aws_iam_role_policy" "too_much" {
  name_prefix = "too-much-"
  role        = aws_iam_role.app.id
  policy = jsonencode({
    Version   = "2012-10-17"
    Statement = [{ Effect = "Allow", Action = "s3:*", Resource = "*" }]
  })
}

resource "aws_iam_instance_profile" "app" {
  name_prefix = "dojo-app-"
  role        = aws_iam_role.app.name
}

data "aws_ami" "ubuntu" {
  most_recent = true
  owners      = ["099720109477"]
  filter {
    name   = "name"
    values = ["ubuntu/images/hvm-ssd-gp3/ubuntu-*-24.04-amd64-server-*"]
  }
}

resource "aws_instance" "app" {
  ami                  = data.aws_ami.ubuntu.id
  instance_type        = "t3.micro"
  iam_instance_profile = aws_iam_instance_profile.app.name

  # The flaw: tokens are optional, so the old metadata service stays on.
  metadata_options {
    http_tokens = "optional"
  }
}

output "bucket" {
  value = aws_s3_bucket.reports.bucket
}

output "role_arn" {
  value = aws_iam_role.app.arn
}
```

Find the three deliberate mistakes: a role with `s3:*` on everything, a metadata service without required tokens, and data with nothing watching it. Now build it:

```bash
terraform init
terraform plan
terraform apply
```

`init` downloads the AWS plugin. `plan` shows what it would do, and changes nothing. Read it. `apply` asks you to type `yes`, then builds everything. It prints the bucket's name and the role's ARN.

@done `terraform apply` finished, and I've saved the outputs.

## Step 5: Turn on the record

**CloudTrail** records API calls, as in [lesson 64](/courses/0064-cloud-detection-and-posture/). In the console, open **CloudTrail → Trails → Create trail**. Log management events, and also **data events** for S3, so that file reads get recorded too. It stores logs in a new bucket.

Remember from the lesson: without data events, you can't prove what was read.

@done My trail is on, and it logs S3 data events.

## Step 6: See what those credentials can reach

Imagine a flaw in a web app on that server. An attacker could use it to fetch the server's role credentials from the metadata service, as [lesson 63](/courses/0063-cloud-foundations-and-iam/) explains. You'll skip that part, and take the role directly, which leaves the same kind of record.

Save the ARN and the bucket in variables:

```bash
ROLE=$(terraform output -raw role_arn)
BUCKET=$(terraform output -raw bucket)
aws sts assume-role --role-arn "$ROLE" --role-session-name lab-test > creds.json
export AWS_ACCESS_KEY_ID=$(jq -r .Credentials.AccessKeyId creds.json)
export AWS_SECRET_ACCESS_KEY=$(jq -r .Credentials.SecretAccessKey creds.json)
export AWS_SESSION_TOKEN=$(jq -r .Credentials.SessionToken creds.json)
aws sts get-caller-identity
aws s3 ls
aws s3 cp "s3://$BUCKET/customers.csv" -
```

You're now the role. Notice that it can list **every** bucket in the account, not only the one it needs. Write down what you ran, and when, in UTC. When you're finished, go back to your own identity, and delete the file:

```bash
unset AWS_ACCESS_KEY_ID AWS_SECRET_ACCESS_KEY AWS_SESSION_TOKEN
rm creds.json
```

@done I've listed what the role could reach, with timestamps, and I've deleted `creds.json`.

## Step 7: Find it in the logs

@help cloudtrail guided

CloudTrail's **Event history** shows management events for 90 days, and you can search it from the terminal:

```bash
aws cloudtrail lookup-events --lookup-attributes AttributeKey=EventName,AttributeValue=AssumeRole --max-results 5
```

Each event's `CloudTrailEvent` field holds the JSON that you read in [lesson 64](/courses/0064-cloud-detection-and-posture/). S3 reads are in your trail's bucket, and they can take a few minutes to appear. For searching a lot of logs, use **Athena**: on the CloudTrail **Event history** page, choose **Create Athena table**. Then you can use SQL:

```sql
SELECT eventtime, eventname, sourceipaddress, useridentity.arn
FROM your_cloudtrail_table
WHERE eventsource = 's3.amazonaws.com'
ORDER BY eventtime DESC
LIMIT 20;
```

Match each row to your notes from the previous step. The practice with `jq` from [the Switchboard machine](/machines/switchboard/) applies here.

@done I've found each of my actions in the logs.

## Step 8: Detect it

@help guardduty guided

**GuardDuty** watches your account for threats. Turn it on, and generate sample findings, so that you can see what they look like. It's free for a trial period, but still check its pricing.

```bash
DETECTOR=$(aws guardduty create-detector --enable --query DetectorId --output text)
aws guardduty create-sample-findings --detector-id "$DETECTOR"
aws guardduty list-findings --detector-id "$DETECTOR" --max-results 5
```

Then write eight detections of your own as saved Athena queries, each validated by repeating the action. Good ones: a role assumed by something unexpected, `StopLogging`, a new access key, a bucket policy made public, and `GetObject` from an unknown address.

@done I have eight detections, each proven by repeating the action.

## Step 9: Respond, and fix it in code

Play out the response from [lesson 64](/courses/0064-cloud-detection-and-posture/): revoke the role's sessions, scope what it could reach, and write a short incident report.

Then fix the causes in `main.tf`, not in the console. Change `http_tokens` to `"required"`. Replace the role's policy with only `s3:GetObject` on your bucket. Remove the extra trust principal. Add a `aws_s3_bucket_public_access_block` for the bucket. Run `terraform plan`, read it, and then `terraform apply`.

Prove that it worked: try the same commands again, and show them being refused. A fix without proof is a hope.

@done The same commands now fail, and I've saved the evidence.

## Step 10: Measure, then destroy

@help prowler guided

**Prowler** checks your account against best practice. The easiest way to run it is with Docker, because its Python package can lag behind new Python versions. Export your credentials, then:

```bash
docker run --rm -e AWS_ACCESS_KEY_ID -e AWS_SECRET_ACCESS_KEY -e AWS_SESSION_TOKEN prowlercloud/prowler:stable aws
```

Run it on both versions, to get a before and an after. If you've already fixed everything, go back one commit with Git, apply, scan, then return. Rank the findings by exposure and sensitivity, as [lesson 64](/courses/0064-cloud-detection-and-posture/) showed, and don't chase them all.

Finish by destroying everything, then check the console, and delete your access key:

```bash
terraform destroy
```

Write your README as a story: architecture, attack path, what the logs showed, the response, the fixes, and proof that it now fails.

@done My environment is destroyed, my key is deleted, and my README tells the story.
