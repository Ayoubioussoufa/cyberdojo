## Step 3: Second stage, your dependencies

@goal Build a small, non-root image. Generate an SBOM with Syft in CycloneDX format and upload it as a build artifact. Fail the build with Trivy when a known-vulnerable base image is used.
@search syft generate sbom cyclonedx | trivy image exit-code severity | github actions upload artifact

@help syft guided

**Syft** lists everything inside an image, which is your SBOM. Install it, then generate one:

```bash
curl -sSfL https://get.anchore.io/syft | sudo sh -s -- -b /usr/local/bin
syft notes-app:latest -o cyclonedx-json=./sbom.cdx.json
```

@help trivy guided

**Trivy** scans images, code and configuration for known problems. With Docker:

```bash
docker run --rm -v /var/run/docker.sock:/var/run/docker.sock aquasec/trivy:latest image --severity HIGH,CRITICAL --exit-code 1 notes-app:latest
```

`--exit-code 1` makes it fail when it finds something, which is what turns a report into a gate. Add both to your workflow, and upload the SBOM as a build artifact.

## Step 6: Sign what you build

@goal Push your image to a registry, sign it with cosign by digest and not by tag, and verify it. Keep the private key out of Git. Your pipeline should sign each image.
@search cosign sign container image | image digest versus tag

@help cosign guided

**cosign** signs images, so that you can prove where one came from. Push your image to a registry, such as GitHub's, then:

```bash
cosign generate-key-pair
cosign sign --key cosign.key ghcr.io/YOUR-NAME/notes-app@sha256:DIGEST
cosign verify --key cosign.pub ghcr.io/YOUR-NAME/notes-app@sha256:DIGEST
```

Sign by **digest**, not by tag, because a tag can move. Keep `cosign.key` out of Git, and in your CI secrets. Later, try keyless signing from CI, which needs no key at all: `cosign sign $IMAGE`, using the workflow's own identity.

@done My pipeline signs each image, and `cosign verify` passes.

## Step 8: Refuse unsafe pods

@goal Create a namespace `app` that enforces the `restricted` Pod Security level. Show a privileged pod being refused and a hardened one running, then add a default-deny NetworkPolicy and least-privilege RBAC.
@search kubernetes pod security admission namespace label | pod security standards restricted | kubernetes default deny network policy
@docs Pod Security Standards | https://kubernetes.io/docs/concepts/security/pod-security-standards/
@docs Network policies | https://kubernetes.io/docs/concepts/services-networking/network-policies/

Kubernetes has a built-in check, called Pod Security. Turn on the strictest level for one namespace:

```bash
kubectl create namespace app
kubectl label namespace app pod-security.kubernetes.io/enforce=restricted
```

Save this as `bad-pod.yaml`, and apply it with `kubectl apply -f bad-pod.yaml`:

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: bad
  namespace: app
spec:
  containers:
    - name: web
      image: nginx:1.29
      securityContext:
        privileged: true
```

It's refused: `violates PodSecurity "restricted:latest"`. Now this one, as `good-pod.yaml`, which is accepted:

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: good
  namespace: app
spec:
  securityContext:
    runAsNonRoot: true
    runAsUser: 1000
    seccompProfile:
      type: RuntimeDefault
  containers:
    - name: web
      image: nginxinc/nginx-unprivileged:1.29
      securityContext:
        allowPrivilegeEscalation: false
        capabilities:
          drop: ["ALL"]
```

Add a default-deny NetworkPolicy and least-privilege RBAC for your app, as in [lesson 74](/courses/0074-kubernetes-and-zero-trust/).

@done The privileged pod is refused, and the hardened one runs.

## Step 9: Add your own rules

@goal Install Kyverno with Helm, and write three policies: one that refuses the `latest` tag, one of your own, and one that requires signed images. See each one refuse something.
@search kyverno validatingpolicy | kyverno verify image signature

@help kyverno guided

**Kyverno** lets you write your own admission rules. Install it with Helm:

```bash
helm repo add kyverno https://kyverno.github.io/kyverno/
helm repo update
helm install kyverno kyverno/kyverno -n kyverno --create-namespace --wait
```

Save this as `no-latest.yaml`. Older guides use `ClusterPolicy`, which Kyverno now marks as deprecated, so use this newer form:

```yaml
apiVersion: policies.kyverno.io/v1
kind: ValidatingPolicy
metadata:
  name: no-latest-tag
spec:
  validationActions: [Deny]
  matchConstraints:
    resourceRules:
      - apiGroups: [""]
        apiVersions: ["v1"]
        operations: ["CREATE", "UPDATE"]
        resources: ["pods"]
  validations:
    - expression: "object.spec.containers.all(c, !c.image.endsWith(':latest'))"
      message: "Use a fixed image version, not :latest."
```

Test it in a namespace without Pod Security, so that you can tell which check refused it:

```bash
kubectl apply -f no-latest.yaml
kubectl create namespace demo
kubectl run a -n demo --image=nginx:latest
kubectl run b -n demo --image=nginx:1.29
```

The first is denied with your message, and the second is created. Write two more policies, and add one that requires signed images, using [Kyverno's image verification docs](https://kyverno.io/docs/).

@done My three policies work, and I've seen each one refuse something.


@help falco guided

**Falco** watches what containers do while they run. Install it with Helm:

```bash
helm repo add falcosecurity https://falcosecurity.github.io/charts
helm repo update
helm install --replace falco --namespace falco --create-namespace --set tty=true --set driver.kind=modern_ebpf falcosecurity/falco
kubectl wait pods --for=condition=Ready --all -n falco --timeout=180s
```

Wait until it's ready, then do something suspicious inside your own pod, and read Falco's log:

```bash
kubectl exec -n demo b -- sh -c 'cat /etc/shadow > /dev/null'
kubectl logs -n falco -l app.kubernetes.io/name=falco -c falco --tail=20
```

Reading a sensitive file should produce an alert. Prove three scenarios. If the driver won't load in your setup, check [the chart's documentation](https://github.com/falcosecurity/charts).
