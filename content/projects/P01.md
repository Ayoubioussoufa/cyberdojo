This is your first real project, so nothing is skipped. By the end you'll have a firewall, a server and a second machine in a private network on your laptop, plus a script that measures how secure the server is. Everything here is used again in later projects, which is why it's worth doing carefully.

@term virtual machine (VM) = A whole computer simulated by software, running inside your real one.
@term snapshot = A saved state of a virtual machine that you can return to.
@term hypervisor = The software that runs virtual machines.

## How your lab will look

@flow Your laptop > VirtualBox > Firewall VM > LAN: Kali + DMZ: Ubuntu server

| Machine | Job | Network | Address |
|---|---|---|---|
| `fw1` (OPNsense) | Firewall between networks | WAN, LAN, DMZ | `192.168.1.1`, `10.10.20.1` |
| `kali1` (Kali Linux) | Your testing machine | LAN | `192.168.1.100` |
| `srv1` (Ubuntu Server) | The server you'll harden | DMZ | `10.10.20.10` |

A **LAN** is a trusted inside network. A **DMZ** is a separate zone for servers, so that if one is broken into, the attacker still can't reach the LAN. Your firewall enforces that.

::: law Your own machines only
Everything you scan here lives on your own laptop. Never point these tools at anything you don't own.
:::

## Step 1: Draw it before you build it

@help drawio guided

**draw.io** is a free diagram tool that runs in your browser, with nothing to install. Open [app.diagrams.net](https://app.diagrams.net/), choose "Create New Diagram" and pick "Blank". Save it to your device as `topology.drawio`.

Drag on three rectangles, and label them with the names from the table above. Draw lines between them, and write each network's range on its line: `192.168.1.0/24` for the LAN and `10.10.20.0/24` for the DMZ. Those `/24` ranges are the subnets you learned in lesson 16.

Then choose **File → Export as → PNG**, and save it as `topology.png`.

Drawing first feels slow. It's how you catch mistakes while they're still free to fix.

## Step 3: Build the firewall

@help virtualbox guided

**VirtualBox** is a free hypervisor. Install it from [virtualbox.org](https://www.virtualbox.org/wiki/Downloads), if you didn't in [lesson 12](/courses/0012-build-your-lab/).

@help opnsense guided

**OPNsense** is a free firewall operating system. Download the `dvd` image for `amd64` from [opnsense.org/download](https://opnsense.org/download/). It arrives compressed, so unpack it to get an `.iso` file.

In VirtualBox, click **New**:

1. Name it `fw1`, choose your ISO, type **BSD**, version **FreeBSD (64-bit)**.
2. Give it 2 GB of memory, 2 CPUs and a 20 GB disk.
3. Before starting it, open **Settings → Network**, and set three adapters:

| Adapter | Attached to | Name | Becomes |
|---|---|---|---|
| 1 | NAT | | WAN, the way out to the internet |
| 2 | Internal Network | `lab-lan` | LAN |
| 3 | Internal Network | `lab-dmz` | DMZ |

An **internal network** is a private cable between VMs that doesn't touch your real network.

Start the VM. It boots into a working system running from the disc image. Log in with username `installer` and password `opnsense`, and follow the prompts to install it to the virtual disk. Choose a new root password when it asks, and write it down. When it's finished, shut down, remove the ISO under **Settings → Storage**, and start the VM again.

At the console menu, log in as `root` and check that WAN and LAN are on the right adapters. Option 1 assigns interfaces, if you need to change them. The LAN address is `192.168.1.1` by default, which matches your plan.

Take a snapshot now: **Machine → Take Snapshot**, and name it `fw-installed`. If you break something later, you can return here in seconds.

@done OPNsense is installed, and I've taken a snapshot.

## Step 4: Build Kali and open the firewall's web page

@help kali guided

**Kali Linux** is a system that comes with security tools already installed. Download the ready-made VirtualBox image from [kali.org/get-kali](https://www.kali.org/get-kali/#kali-virtual-machines), unpack it, and open the `.vbox` file. Before starting it, set its network adapter to **Internal Network**, named `lab-lan`. Give it 4 GB of memory if you can.

Log in with `kali` / `kali`, and change that password straight away with `passwd`. It got an address from the firewall automatically, so check:

```bash
ip a
```

You should see an address beginning `192.168.1.`. Now open the browser inside Kali, and go to `https://192.168.1.1/`. Accept the certificate warning, which is expected on a brand-new firewall. Log in as `root` with the password you chose.

Add the third network. Go to **Interfaces → Assignments**, add the unused interface, and name it `DMZ`. Open it, tick **Enable**, set IPv4 to **Static**, and give it the address `10.10.20.1/24`. Save and apply.

@done From Kali, I can log in to the firewall's web page, and the DMZ interface is up.

## Step 5: Write rules with reasons

A firewall rule says what may pass from where to where. A new interface has no rules, so everything is blocked: that's **default deny**, from [lesson 21](/courses/0021-firewalls-and-segmentation/).

In **Firewall → Rules → DMZ**, add these, and fill in each rule's description with your reason.

| From | To | Port | Action | Reason |
|---|---|---|---|---|
| DMZ net | any | 80, 443 | Allow | The server needs updates |
| DMZ net | any | 53 | Allow | The server needs DNS |
| DMZ net | LAN net | any | Block | A hacked server must not reach the LAN |

Order matters, because the first match wins. Put the **block** rule at the top.

In **Firewall → Rules → LAN**, the default rule lets the LAN reach everything, which is fine for a lab. Create `firewall-rules.md` in your repository, with the same table, and commit it.

@done Every firewall rule has a one-line reason, and they're in my repository.

## Step 6: Build the server

@help ubuntu-server guided

Download **Ubuntu Server** LTS from [ubuntu.com/download/server](https://ubuntu.com/download/server). Create a VM named `srv1` with 2 GB of memory and a 25 GB disk, and attach one adapter to the internal network `lab-dmz`.

During the install, when it reaches the network screen, edit the interface to use a manual IPv4 address:

| Field | Value |
|---|---|
| Subnet | `10.10.20.0/24` |
| Address | `10.10.20.10` |
| Gateway | `10.10.20.1` |
| Name server | `10.10.20.1` |

Tick **Install OpenSSH server**, and don't add any extra software. Each extra service is one more thing to defend. When it finishes, remove the ISO, reboot, and take a snapshot called `srv-fresh`.

Sign in, and make sure that it can reach the internet through your firewall:

```bash
sudo apt update
```

If it can't, check your DMZ rules and DNS in OPNsense. That's normal troubleshooting, and worth writing down in your notes.

@help ssh guided

**SSH** lets you control a server from another machine over an encrypted connection. You met it in [lesson 13](/courses/0013-ssh-and-your-first-wargame/). Keys are much safer than passwords, so set them up from Kali:

```bash
ssh-keygen -t ed25519
ssh-copy-id YOUR-USER@10.10.20.10
ssh YOUR-USER@10.10.20.10
```

The first command makes your key pair. The second copies the public half to the server. The third logs you in, and it shouldn't ask for the server password now.

@done I can log in to `srv1` from Kali with an SSH key.

## Step 7: Write your audit script

@help bash guided

A **Bash script** is a list of commands in a file. Here's your audit tool, which uses the checks you met in [lesson 24](/courses/0024-bash-scripting/). It only reads, so it can't harm anything. Create `audit.sh` in your repository:

```bash
#!/usr/bin/env bash
# audit.sh: checks a Linux server for common weaknesses.
# Run it with sudo. It only reads, and it changes nothing.
set -u

problems=0

pass() { echo "[PASS] $1"; }
fail() { echo "[FAIL] $1"; problems=$((problems + 1)); }

# 1. Only root should have UID 0.
extra=$(awk -F: '$3 == 0 && $1 != "root" {print $1}' /etc/passwd)
if [ -z "$extra" ]; then pass "Only root has UID 0"; else fail "Extra UID 0 accounts: $extra"; fi

# 2. No world-writable files in /etc.
writable=$(find /etc -type f -perm -002 2>/dev/null)
if [ -z "$writable" ]; then pass "No world-writable files in /etc"; else fail "World-writable: $writable"; fi

# 3. List SUID programs, for a human to review.
count=$(find / -xdev -type f -perm -4000 2>/dev/null | wc -l)
echo "[INFO] $count SUID programs found. Compare with last time."

# 4. SSH must refuse root logins and passwords. `sshd -T` prints the settings
#    really in force, including those from sshd_config.d.
settings=$(sshd -T 2>/dev/null)
if echo "$settings" | grep -q '^permitrootlogin no'; then pass "SSH refuses root logins"; else fail "SSH may allow root logins"; fi
if echo "$settings" | grep -q '^passwordauthentication no'; then pass "SSH refuses passwords"; else fail "SSH may allow passwords"; fi

# 5. Show what's listening, for a human to explain.
if command -v ss >/dev/null; then
  echo "[INFO] Listening ports:"
  ss -tuln | awk 'NR > 1 {print "       " $1, $5}'
fi

# 6. Are updates waiting?
if command -v apt >/dev/null; then
  pending=$(apt list --upgradable 2>/dev/null | grep -c upgradable)
  if [ "$pending" -eq 0 ]; then pass "No updates waiting"; else fail "$pending updates waiting"; fi
fi

echo
echo "Finished with $problems problems."
exit "$problems"
```

Read each check, and make sure that you could explain it. Then:

@help shellcheck guided

**ShellCheck** finds mistakes in shell scripts. On Kali:

```bash
sudo apt install shellcheck
shellcheck audit.sh
chmod +x audit.sh
```

No output from `shellcheck` means no problems found. Copy the script to the server, then run it, and save the result. This is your **before** picture.

```bash
scp audit.sh YOUR-USER@10.10.20.10:
ssh YOUR-USER@10.10.20.10 'sudo ./audit.sh' | tee audit-before.txt
```

`tee` shows the output and also saves it to a file. Commit both files.

Add two checks of your own: for example, accounts with empty passwords, or files in `/tmp` that can be run.

@done `audit.sh` passes ShellCheck, and `audit-before.txt` is in my repository.

## Step 8: Harden the server

Do one change at a time, and log each in `HARDENING.md`: what you changed, and why.

**Turn off root and password logins.** Keep your SSH session open while you do this, so that a mistake can't lock you out.

```bash
sudo tee /etc/ssh/sshd_config.d/00-hardening.conf <<'EOF'
PermitRootLogin no
PasswordAuthentication no
EOF
sudo sshd -t && sudo systemctl restart ssh
```

`sshd -t` tests the settings, and the restart only runs if the test passes. Open a **second** terminal and log in again before you close the first.

@help ufw guided

**ufw** is Ubuntu's simple host firewall. It's a second layer inside the server, in case the network firewall is ever wrong.

```bash
sudo ufw default deny incoming
sudo ufw default allow outgoing
sudo ufw allow from 192.168.1.0/24 to any port 22 proto tcp
sudo ufw enable
sudo ufw status verbose
```

Allow SSH **before** you run `enable`, or you'll cut yourself off.

**Turn on automatic security updates:**

```bash
sudo apt install unattended-upgrades
sudo dpkg-reconfigure -plow unattended-upgrades
```

@help lynis guided

**Lynis** audits a whole system and gives you a score. It checks far more than your script does.

```bash
sudo apt install lynis
sudo lynis audit system --quick | tee lynis.txt
grep "Hardening index" lynis.txt
```

Fix the suggestions that make sense, and write down the ones that you decide to leave, with your reason. That's an **accepted risk**, and it's one of the most impressive things a junior can show.

Run your audit again, and save it as `audit-after.txt`. Commit everything.

@done My audit shows fewer failures, and every remaining one has a written reason.

## Step 9: Attack surface, and writing it up

@help nmap guided

**Nmap** shows which ports are open, as you learned in [lesson 22](/courses/0022-scanning-with-nmap/). From Kali:

```bash
nmap -sV -oN nmap-after.txt 10.10.20.10
```

Explain each open port in your README. If you can't explain one, it probably shouldn't be open.

Now restore the snapshot `srv-fresh`, scan it, and save that as `nmap-before.txt`. Then restore your hardened state. Those two files are your proof.

Your README should open with the diagram, then two sentences on what this is. Add a **Findings** section with what the audit caught and how you fixed it, and a **Rebuild** section explaining how someone else could do this.

::: tip Test your README
Follow your own rebuild steps on a fresh VM, or ask a friend to. Everything they get stuck on is a fix for you.
:::
