A packet capture is a recording of network traffic, and it's the closest thing to CCTV on a network. In this project you become the detective: three cases, each one written up so that a stranger could check your work.

@term packet capture (pcap) = A file that records network traffic, packet by packet.
@term display filter = A Wireshark expression that hides every packet that doesn't match.

## Step 2: Install Wireshark, and capture something yourself

@help wireshark guided

**Wireshark** shows captured traffic in a form that humans can read. It's already on Kali. On your own computer, install it from [wireshark.org/download](https://www.wireshark.org/download.html).

@help tcpdump guided

**tcpdump** captures packets from the command line, which is how you capture on a server with no screen. On Kali, in one terminal:

```bash
sudo tcpdump -i eth0 -w first.pcap port 53 or port 443
```

`-i` picks the network interface, `-w` writes to a file, and the rest is a filter. In a second terminal, cause some traffic:

```bash
curl -s https://example.com > /dev/null
```

Press `Ctrl+C` in the first terminal, then open it: `wireshark first.pcap`. You've just captured your own DNS lookup and web connection. Find them.

| Pane | Shows |
|---|---|
| Top | One line per packet |
| Middle | The layers of the selected packet |
| Bottom | The raw bytes |

These filters go in the bar at the top:

| Filter | Shows |
|---|---|
| `dns` | DNS only |
| `ip.addr == 10.0.0.5` | Traffic to or from one address |
| `tcp.flags.syn == 1 && tcp.flags.ack == 0` | New connection attempts |
| `http.request` | Web requests |
| `tls.handshake.extensions_server_name` | Encrypted connections, showing the site's name |

Two features do most of the work. **Statistics → Conversations** shows who talked to whom, and how much. **Right-click a packet → Follow → TCP Stream** shows one whole conversation.

@done I've captured my own traffic, and I can find my DNS lookup in it.

## Step 3: Choose three cases

Pick three captures of rising difficulty from a source built for this.

| Source | Good for |
|---|---|
| [Wireshark sample captures](https://wiki.wireshark.org/SampleCaptures) | Your first case: normal protocols, and scans |
| [Malware-Traffic-Analysis.net](https://www.malware-traffic-analysis.net/training-exercises.html) | Real infections, written as exercises |
| [CyberDefenders](https://cyberdefenders.org/blueteam-ctf-challenges/) | Investigations with questions to check against |

::: law Handle samples with care
Some captures contain real malware. Open them only in Wireshark on your Kali VM, and don't extract or run any file from them. Read each site's rules on passwords before you unpack anything.
:::

Save the name and link of each case in your README. Don't commit the capture files themselves, as they may be large or hold harmful content.

## Step 4: Solve case 1, timeline first

Don't answer questions yet. First, build a **timeline**: what happened, in order, with times. Use `Statistics → Conversations` to find the busiest pairs, then work through them.

| Time (UTC) | Packet | What the capture shows |
|---|---|---|
| 09:14:02 | 102 | `10.0.0.5` sends SYN to ports 1–1024 of `10.0.0.9` |
| 09:14:40 | 2015 | `10.0.0.9` answers SYN-ACK on 22 and 80 only |

Record the **packet number** each time, so that anyone can check your claim. To set Wireshark to UTC, use **View → Time Display Format → UTC Date and Time of Day**.

@help cyberchef guided

**CyberChef** decodes data in your browser, and nothing gets uploaded. Open [gchq.github.io/CyberChef](https://gchq.github.io/CyberChef/). If you find a base64 string in a capture, paste it in as the input, and drag **From Base64** to the recipe.

@help virustotal guided

**VirusTotal** checks whether a hash or a domain is known to be malicious. Search only for **hashes and domains**. Don't upload files, because uploads can be seen by others.

Keep your facts and your guesses apart:

| Fact | Inference |
|---|---|
| "Packet 2015 shows port 22 is open" | "They probably planned to log in over SSH" |

Now write `case-1.md`. It needs a summary, the timeline, the evidence (filters and packet numbers), indicators, recommendations, and a section called **What I got wrong first**. That last section shows your thinking, and senior reviewers love it.

@done `case-1.md` has a timeline with packet numbers, and facts kept apart from inferences.

Start with **Statistics → Conversations**, sorted by bytes. An exfiltration is often one large upload to an unusual address. An infection often shows a download, then regular small connections to the same place, which are check-ins. For DNS, filter on `dns`, and look for very long or random-looking names.
